# Context Bridge

> 사용자의 정보를 무조건 AI에 전달하는 것이 아니라, 질문에 필요한 맥락만 추천하고 사용자가 직접 승인한 정보만 활용하는 사용자 통제형 AI 서비스입니다.

## 1. 프로젝트 배경

일반적인 생성형 AI는 사용자의 상황과 제약을 충분히 알지 못해 매번 같은 설명을 반복하게 하거나, 반대로 너무 많은 개인정보를 한꺼번에 사용하게 만들 수 있습니다.

Context Bridge는 다음 문제를 해결하는 것을 목표로 합니다.

- 사용자가 자신의 정보를 매번 반복해서 설명해야 하는 문제
- 질문과 관련 없는 개인정보까지 AI에 전달될 수 있는 문제
- 고령층과 AI 초보자가 복잡한 설정을 이해하기 어려운 문제
- AI가 저장한 정보가 언제, 어떻게 사용되는지 알기 어려운 문제

## 2. 핵심 아이디어

질문이 입력되면 전체 사용자 정보를 그대로 보내지 않고 다음 흐름으로 처리합니다.

```text
사용자 질문
→ 질문 의도 및 결정 영역 분석
→ 관련 맥락 후보 추천
→ 민감도·최신성·충돌 검사
→ 사용자 승인 또는 거절
→ 승인된 맥락만 AI에 전달
→ 개인화 답변 생성
→ 새 정보 저장 여부를 다시 사용자에게 확인
```

## 3. 핵심 원칙

1. 사용자가 승인한 정보만 최종 생성 모델에 전달합니다.
2. 거절한 카드의 값, 제목, ID, 존재 여부를 프롬프트와 로그에 포함하지 않습니다.
3. 민감정보는 기본 선택 해제 상태로 제공하고 사용자가 직접 승인하도록 합니다.
4. 기밀정보는 모델에 전달되지 않도록 차단합니다.
5. 모든 제약을 무조건 적용하지 않고 현재 질문과 관련된 제약만 검사합니다.
6. 오래된 정보, 현재 질문과 프로필의 충돌, 카드 간 모순을 검사합니다.
7. 생성된 답변을 다시 검증해 개인정보 노출과 필수 제약 위반을 확인합니다.
8. 답변에서 발견된 새 정보는 자동 저장하지 않고 사용자 승인 후에만 저장합니다.

## 4. 주요 기능

### 맥락 자동 추천

사용자의 질문을 분석해 답변에 필요한 정보만 후보 카드로 추천합니다.

### 맥락 승인

사용자는 추천된 카드 중 사용할 정보만 직접 선택할 수 있습니다.

### 승인 기반 기억

답변 중 새롭게 확인된 정보는 자동 저장하지 않고 `저장` 또는 `무시`를 선택하게 합니다.

### 프로필 관리

사용자는 목적에 따라 여러 프로필을 만들고 선택할 수 있습니다.

예시:

- 대학생 프로필
- 시니어 프로필
- 취업 준비 프로필
- 여행 프로필

### 정보 분류

사용자 정보는 이해하기 쉬운 네 가지 기준으로 관리합니다.

- 기본정보
- 취향과 원하는 방향
- 목표와 목적
- 꼭 지켜야 할 주의사항과 제약

### 접근성 기능

- 큰 글씨와 명확한 버튼
- 음성 입력
- 답변 읽어주기
- 특수문자를 자연스럽게 제외한 음성 읽기
- 고령층과 AI 초보자를 고려한 간단한 승인 흐름

## 5. 사용자 경험 방향

기존의 복잡한 설정 화면보다 채팅을 중심으로 설계했습니다.

```text
프로필 선택
→ 질문 입력
→ 필요한 맥락 확인
→ 사용할 정보 승인
→ 답변 확인
→ 새 정보 저장 여부 선택
```

주요 UX 원칙은 다음과 같습니다.

- 처음 사용하는 사람도 설명 없이 사용할 수 있어야 합니다.
- 한 화면에서 너무 많은 선택지를 보여주지 않습니다.
- 전문 용어보다 사용자가 이해할 수 있는 표현을 사용합니다.
- 승인, 거절, 저장, 무시 상태가 명확하게 보여야 합니다.
- 기능이 UI에 가려지지 않도록 핵심 흐름을 우선합니다.

- 팀원 간 요구사항 정리와 역할 조율

주요 공유 파일:

```text

docs/FRONTEND_HANDOFF.md
src/types.ts
mock-server.mjs
.env.example
```

프론트엔드는 Mock API로 먼저 개발하고, 이후 실제 백엔드 API 주소로 교체할 수 있도록 구성합니다.

## 8. 데이터 처리 구조

```text
전체 사용자 카드
→ 질문 관련 후보 검색
→ 의미 관련성 평가
→ 정책 및 안전성 검사
→ 사용자 승인
→ 승인 카드만 별도 객체로 구성
→ 생성 모델 호출
→ 출력 검증
```

생성 모델에는 전체 프로필이 아니라 승인된 최소 정보만 전달합니다.

## 9. API 흐름

```text
POST /api/proposals
질문에 필요한 맥락 후보 생성

POST /api/approvals
사용자가 승인한 맥락 확정

POST /api/generate
승인된 맥락만 사용해 답변 생성

POST /api/memory-suggestions
답변에서 새롭게 발견된 저장 후보 제안

POST /api/memories
사용자가 승인한 정보만 저장
```

실제 API 이름과 요청 형식은 `contracts` 및 프론트 전달 문서를 기준으로 관리합니다.

## 10. 주요 개선 과정

초기 버전에서는 태그와 고정된 의도 분류에 크게 의존해 새로 추가한 사용자 카드가 추천되지 않는 문제가 있었습니다.

이를 다음과 같이 개선했습니다.

- 하드코딩된 태그 의존도 축소
- 사용자 정의 카드 지원
- 질문과 카드의 의미 기반 관련성 평가
- 최근 정보와 오래된 정보 구분
- 카드 간 충돌 검사
- 질문과 프로필 정보의 모순 검사
- 관련 없는 `hard_limit` 자동 제외
- 승인 전후 데이터 흐름 분리
- 답변 후 개인정보 및 제약 위반 재검증
- 자동 저장 제거 및 승인 기반 저장 적용
- 복잡한 대시보드형 UI에서 채팅 중심 UI로 변경
- 고령층도 사용할 수 있도록 승인 단계를 단순화

## 11. 테스트 우선순위

현재 프로젝트는 다음 핵심 흐름을 우선 검증합니다.

```text
계정 생성
→ 프로필 선택
→ 질문 입력
→ 맥락 추천
→ 승인 및 거절
→ 승인 맥락 기반 답변
→ 답변 검증
→ 기억 저장 승인
```

필수 테스트 항목:

- 거절한 맥락이 모델 입력에 포함되지 않는지
- 승인한 맥락만 답변에 반영되는지
- 다른 사용자의 프로필에 접근할 수 없는지
- 기밀정보가 차단되는지
- 관련 없는 제약이 적용되지 않는지
- 오래된 정보와 충돌 정보가 표시되는지
- 저장하지 않은 새 정보가 DB에 남지 않는지
- 음성 입력과 답변 읽기가 정상 작동하는지

## 12. 프로젝트 목표

Context Bridge의 목표는 단순한 개인화 챗봇이 아닙니다.

사용자가 자신의 정보를 통제하면서도 AI의 도움을 더 쉽게 받을 수 있도록 만드는 것이 핵심입니다.

> 필요한 정보만, 사용자가 확인한 뒤, 안전하게 AI와 연결합니다.

## 13. 전체 프로젝트 진행 방법

프로젝트는 기능을 한꺼번에 구현하기보다 아래 순서대로 진행합니다.

### 1단계: 요구사항과 API 계약 확정

먼저 기획, 프론트엔드, 백엔드가 공통으로 사용할 용어와 데이터 구조를 확정합니다.

확정해야 할 핵심 항목:

- 프로필 구조
- 사용자 정보 카드 구조
- 맥락 추천 결과 구조
- 승인 및 거절 데이터 구조
- 답변 생성 요청과 응답 구조
- 기억 저장 제안 구조
- 오류 응답 형식

API 계약은 다음 위치에서 관리합니다.

```text
contracts/
docs/FRONTEND_HANDOFF.md
src/types.ts
```

프론트엔드와 백엔드는 같은 타입 이름과 필드명을 사용해야 합니다.

### 2단계: 프론트엔드 Mock 개발

백엔드가 완성되기 전에는 Mock 서버를 사용해 프론트엔드 흐름을 먼저 구현합니다.

우선 구현할 화면:

1. 로그인 또는 사용자 선택
2. 프로필 선택
3. 채팅 질문 입력
4. 추천 맥락 카드 확인
5. 승인 및 거절
6. 개인화 답변 표시
7. 새 정보 저장 또는 무시
8. 프로필 및 접근성 설정

### 3단계: 백엔드 핵심 파이프라인 구현

백엔드는 아래 순서로 구현합니다.

```text
인증 확인
→ 사용자 프로필 조회
→ 질문 분석
→ 관련 카드 검색
→ 의미 관련성 평가
→ 정책 및 민감도 검사
→ 후보 반환
→ 사용자 승인 수신
→ 승인된 카드만 생성 모델에 전달
→ 답변 검증
→ 저장 후보 제안
```

### 4단계: Supabase 연결

Mock 데이터로 핵심 흐름을 확인한 뒤 실제 Supabase를 연결합니다.

연결 대상:

- 사용자 계정
- 프로필
- 사용자 정보 카드
- 질문 기록
- 승인 기록
- 기억 저장 제안
- 저장된 기억

### 5단계: 실제 API 통합

프론트엔드의 Mock API 주소를 실제 백엔드 주소로 변경합니다.

통합 시 반드시 확인할 항목:

- 요청 및 응답 필드명 일치
- 사용자 인증 토큰 전달
- 승인된 카드 ID만 전송
- 오류 메시지 처리
- 로딩 및 재시도 처리
- 승인하지 않은 정보가 생성 요청에 포함되지 않는지 확인

### 6단계: E2E 테스트

최종 사용자가 실제로 사용하는 순서대로 테스트합니다.

```text
회원가입 또는 로그인
→ 프로필 생성
→ 정보 카드 등록
→ 질문 입력
→ 추천 카드 확인
→ 일부 승인 및 일부 거절
→ 답변 생성
→ 답변 검증
→ 새 정보 저장 또는 무시
→ 히스토리 확인
```

### 7단계: 배포 및 데모 점검

- 프론트엔드 배포
- 백엔드 API 배포
- Supabase 운영 환경 연결
- 환경변수 등록
- 실제 계정으로 데모 리허설
- 실패 시 복구 시나리오 준비

- 전체 사용자 정보를 생성 모델에 직접 전달하지 않습니다.
- 승인 전 후보 데이터와 승인 후 생성 데이터를 별도로 관리합니다.
- 승인 ID를 기준으로 서버가 실제 카드 값을 다시 조회합니다.
- 클라이언트가 임의로 카드 값을 수정해 생성 요청에 넣지 못하게 합니다.
- 거절한 정보는 생성 프롬프트와 로그에서 제외합니다.
- 데이터 접근 권한은 Supabase RLS와 백엔드 인증에서 모두 검사합니다.

- Vite 환경변수는 `VITE_` 접두사가 있어야 브라우저에서 읽을 수 있습니다.
- 배포 환경에서는 Vercel 또는 서버 플랫폼의 환경변수 설정 화면에 등록합니다.

## 22. 테스트 전략

### 단위 테스트

- 질문 의도 분석
- 관련성 점수 계산
- 민감정보 분류
- 제약 필터링
- 승인 카드 추출
- 출력 검증

### API 테스트

- 인증 없는 요청은 `401`
- 다른 사용자 데이터 접근은 `403` 또는 `404`
- 존재하지 않는 프로필은 `404`
- 잘못된 요청 구조는 `400`
- 승인되지 않은 카드가 포함되면 차단
- 기밀정보 전달 시 차단

### E2E 테스트

최소 다음 시나리오를 통과해야 합니다.

1. 대학생 사용자가 자신의 프로필로 질문합니다.
2. 서버가 관련 카드만 추천합니다.
3. 사용자가 일부 카드만 승인합니다.
4. 생성 모델에는 승인 카드만 전달됩니다.
5. 답변이 승인된 정보와 필수 제약을 반영합니다.
6. 거절 카드 정보는 답변과 로그에 나타나지 않습니다.
7. 답변 후 새 정보가 저장 후보로 표시됩니다.
8. 사용자가 저장을 눌렀을 때만 DB에 저장됩니다.

4. 사용자가 사용할 정보를 승인합니다.
5. 승인 정보에 근거한 확인 항목과 다음 행동을 제공합니다.

## 25. 완료 기준

프로젝트는 화면이 많다고 완성된 것이 아닙니다.

다음 조건을 만족하면 핵심 버전이 완성된 것으로 판단합니다.

- 신규 사용자가 설명 없이 핵심 흐름을 사용할 수 있음
- 질문에 관련된 카드가 안정적으로 추천됨
- 사용자가 승인한 정보만 모델에 전달됨
- 거절한 정보가 프롬프트와 로그에 남지 않음
- 다른 사용자 데이터에 접근할 수 없음
- 민감정보가 기본 해제되거나 정책에 따라 차단됨
- 답변 후 정보가 자동 저장되지 않음
- 핵심 E2E 테스트가 통과함
- 로컬과 배포 환경에서 동일한 흐름이 작동함
- 발표 중 사용할 데모 시나리오가 반복해서 성공함
